# Миссия: демо-проект «Demo» с автотестами и онбординг по разделам

Записано 29.09.2026 по просьбе владельца. Цель: тот, кто скачал test_hub с GitHub, за 5 минут
видит, как система работает — без доступа к нашим стендам и без проекта VSHGU.

## Что должно получиться

### 1. Демо-проект `Demo` внутри репозитория

- Папка `demo/` в корне test_hub — маленький, самодостаточный pytest-проект в том же стиле, что
  `auto_tests_vshgu` (папки `tests/api/<раздел>`, `tests/ui/<раздел>`, `tests/e2e`, маркеры
  `api`/`ui`/`smoke`, `allure.title`/`allure.step`, `--env` с одним стендом `local`):
  - 3–4 раздела (например `users`, `orders`, `catalog`, `auth`), суммарно 25–40 тестов;
  - тесты ходят на **встроенный демо-сервис**: маленькое FastAPI-приложение `demo/app/`
    (несколько JSON-эндпоинтов + 3–4 HTML-страницы: логин, список, карточка), которое test_hub
    поднимает сам на отдельном порту (`TH_DEMO_PORT`, по умолчанию 8710) при старте, если
    включено `TH_DEMO=1` (по умолчанию включено на пустой БД, см. ниже);
  - UI-тесты — Playwright по этим страницам (headless), API — requests;
  - часть тестов намеренно разная по исходу: большинство passed, 2–3 failed «по сценарию»
    (баг в демо-сервисе, описанный в docstring), 1–2 skipped, 1 xfail с причиной, 1 «флаки»
    (падает по счётчику запусков) — чтобы дашборд, флаки и известные дефекты были не пустыми;
  - `demo/routes.tsv` — маршруты демо-сервиса для карты покрытия, часть без тестов.
- Сид: на пустой БД (первый запуск) test_hub создаёт проект `Demo` (path = `<repo>/demo`,
  venv = venv самого test_hub, стенд `local` с URL демо-сервиса, цвет из палитры) и одно
  выключенное расписание. Пользователи seed — как сейчас. Проект `VSHGU` и `bike_fit`/`Velo_bot`
  на чужой машине не сидировать: их пути не существуют (сейчас `SEED_PROJECTS` и
  `_seed_vshgu_project` жёстко прописаны — сделать так, чтобы сидировались только при наличии
  пути на диске; у владельца всё остаётся как есть).
- Прогон демо-проекта работает через обычный раннер (`app/core/runner.py`), без особых веток.
- `README.md`: раздел «Быстрый старт с демо» — 5 команд от клона до первого прогона и allure.

### 2. Онбординг по разделам и шагам

- При первом входе (флаг `users.onboarded`, он уже есть) — пошаговый тур: подсветка элемента +
  подсказка «шаг N из M», кнопки «Дальше / Пропустить», прогресс. Шаги: Проекты → карточка
  Demo → страница проекта (вкладки Дашборд/Запуск/Расписания/История/Флаки) → выбрать раздел и
  «Запустить выбранное» → лента прогона и отчёт Allure → Покрытие → Известные дефекты → Суперадминка
  (только для superadmin). Тур можно перезапустить из меню пользователя («Показать тур»).
- Реализация без внешних библиотек (CDN у нас нет): `ui/tour.js` + стили в `ui/style.css` по
  токенам `DESIGN.md`, шаги описаны данными (селектор, текст, страница), переход между
  страницами сохраняет позицию тура в `localStorage`.
- Тексты на русском, короткие, по одному действию на шаг.

## Ограничения

- Существующие тесты `tests/` проходят; добавить тесты: сид Demo на пустой БД (без реальных
  путей), запуск демо-сервиса, API тура (если появится), тур без браузера — как
  `tests/test_project_tabs.py`.
- Стенды VSHGU не трогать. Ключи/секреты в демо не нужны.
- Коммиты небольшие, сообщения на русском. Скриншоты тура в `docs/screenshots/demo_tour_*.png`.

## Приёмка

- На чистом клоне (пустая `workspace/`): `.venv/bin/python -m app.main` → на `/projects` есть
  Demo, стенд `local`, демо-сервис отвечает; «Запустить всё» → прогон завершился, отчёт Allure
  открывается, на дашборде есть числа, во «Флаки» и «Известных дефектах» есть строки.
- Первый вход qa/qa запускает тур, «Пропустить» и «Показать тур» работают.
