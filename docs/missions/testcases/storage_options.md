# Записка: где хранить тест-кейсы

Этап 1 миссии `docs/missions/2026-09-29_testcases_tab.md`. Три варианта хранения для
будущей вкладки «Тест-кейсы» на странице проекта. Код `app/`/`ui/` не менялся,
стенды и Test IT не вызывались — только чтение исходников.

## Что уже есть в коде (база для сравнения)

- **test_hub** строит дерево разделов проекта чисто файловым сканом, без БД
  (`app/core/sections.py`): `discover()` рекурсивно ищет `test_*.py` под
  `tests/api/<area>`, `tests/ui/<area>`, `tests/e2e`, кэширует в
  `workspace/sections/<project>/sections.json`, инвалидирует кэш по
  `mtime_signature()` (количество файлов + сумма mtime). Это ровно тот же приём,
  которым в любом из вариантов ниже придётся строить дерево разделов для кейсов.
- Статус «последнего прогона» у test_hub **не** лежит в `runs.counts`
  (`app/db.py:44-57`) — там только агрегат `{status: count}` по всему прогону
  (`app/core/allure_report.py::counts_from_tests`). Статус конкретного теста
  достаётся отдельно: по `last_run_id` стенда открываются allure-results этого
  прогона (`allure_report.parse_results(results_dir)`) и там ищется запись по
  `fullName`. nodeid → fullName конвертирует `_nodeid_to_full_name()`
  (`app/core/xfail_registry.py:243-256`) — своя копия в каждом модуле
  (`flaky`, `coverage`, `xfail_registry`, `tg_bot`), общей зависимости
  сознательно нет. Любой из трёх вариантов будет вешать статус кейса тем же
  способом: nodeid кейса → fullName → поиск в allure-results последнего прогона.
- Хороший прецедент «второй источник истины поверх allure» уже есть —
  `xfail_registry` (`app/core/xfail_registry.py`): таблица
  `xfail_registry(project, stand, test, reason, first_seen, last_run_id, state,
  issue_url, note)`, апсертится `recalc()` после каждого прогона
  (`runner.py::_finalize` → `xfail.recalc`), а поля, отредактированные вручную
  через `PUT /api/projects/{name}/xfail/{id}` (`issue_url`, `note`), пересчётом
  не затираются (`recalc()` явно берёт их из `existing`, если новый прогон их не
  переопределил — `xfail_registry.py:186-206`).
- В `auto_tests_vshgu_cloude` уже есть готовый конвейер «код → черновик →
  Test IT»:
  - `tools/test_cases/generate.py` — статический (без импорта/запуска тестов)
    ast-разбор: список nodeid через `pytest --collect-only`, дальше из декораторов
    и тела функции достаются `allure.title`/`allure.severity`/`allure.feature`/
    `allure.story`, докстринг (→ предусловие) и шаги `with allure.step("...")`
    (`_StepVisitor`). Приоритет — по карте severity→priority
    (`PRIORITY_BY_SEVERITY`), роль — эвристика по именам аргументов теста
    (`guess_roles`). Результат — markdown `docs/test_cases/<area>.md` по
    `TEMPLATE.md`: заголовок `### TC-<AREA>-NNN <title>`, хэш шагов
    (`<!-- steps-hash: ... -->`), строка `- Автотест: <nodeid>`, приоритет/тип/роли,
    предусловия, таблица шагов. Идемпотентно по ключу «- Автотест: nodeid»:
    повторный запуск не трогает вручную отредактированные поля, а при
    рассинхроне steps-hash только помечает заголовок `<!-- обновить -->` —
    текст правит человек.
  - `tools/test_cases/testit_sync.py` — синк этих md-файлов в Test IT Public
    API v2 (`Authorization: PrivateToken <TESTIT_TOKEN>`): секция проекта по
    имени области, work item типа `TestCases` по кейсу, идемпотентность —
    поиск существующего work item по названию + тегу `autotest:<nodeid>`
    (`POST /api/v2/workItems/search`, `find_work_item`), при `--apply` id
    заливки дописывается обратно в md (`- Test IT: <id>`).
  - Ключи (`TESTIT_URL`, `TESTIT_TOKEN`, `TESTIT_PROJECT_ID`) — только в `.env`
    `auto_tests_vshgu_cloude` (`.env.example:93-96`). В test_hub таких
    переменных сейчас нет вообще.
  - Прецедент `tools/test_cases/achievements_cases.py` показывает, что кейсы
    **без привязки к автотесту** в Test IT уже существуют (владелец разрешил
    для миссии по достижениям) — связь «кейс ⇄ nodeid» не обязана быть 1:1.

## Вариант А. Генерировать на лету, ничего не хранить

**Источник истины** — сам код автотестов (docstring/`allure.title`/
`allure.step`) в репозитории проекта. Кейс = автотест; отдельной сущности
«тест-кейс» не существует.

**Поток данных.** Пользователь открывает вкладку «Тест-кейсы» → GET
`/api/projects/{name}/testcases` → роут не читает никакую таблицу, а сканирует
`project.path/tests` тем же обходом, что `sections.py::discover()`, но вместо
одного `tests_count` на файл гоняет ast-разбор в духе
`generate.py::parse_module` (title/severity/docstring/steps) — эту логику
придётся портировать в test_hub, т.к. `auto_tests_vshgu_cloude` — отдельный
репозиторий, а test_hub работает с разными проектами, а не только с ним. Кэш —
JSON на диск + инвалидация по `mtime_signature()`, как у `sections.py`. Статус
последнего прогона довешивается отдельным проходом (см. «Что уже есть» выше).
Кейс без автотеста в этой модели в принципе невозможен — значит фильтр «нет
автотеста» из миссии тут пустой по построению.

**Правка кейса** — только правка исходного кода теста (docstring/
`allure.title`/`allure.step`) тем, кто пишет автотест (QA-инженер, у которого
есть доступ к репозиторию тестов), через обычный git commit + деплой/git pull
теста. В UI test_hub кнопки «сохранить кейс» нет и не может быть — нечего
сохранять отдельно от кода.

**Версионирование** — то же, что версионирование самого файла теста: `git log`/
`git blame` по репозиторию автотестов. Отдельной истории «кейс менялся, тест —
нет» не существует, откат кейса = откат коммита с тестом (откатится и логика
теста).

**Переименование автотеста/nodeid** — так как nodeid и есть единственный
идентификатор кейса, переименование — это не «правка», а «кейс с этим
идентификатором исчез, появился кейс с другим идентификатором». Никакой
привязки старого к новому нет: карточка просто перестаёт быть в дереве, новая
появляется с пустой историей прогонов (пока не будет нового прогона на этом
nodeid). Починка невозможна автоматически — только следующий прогон + то, что
человек заметит пропажу по имени в дереве разделов.

**Объём работы на этап 2** (укрупнённо):
- модуль `app/core/testcases.py`: перенос ast-логики `generate.py`
  (title/severity/step/docstring) на произвольный `project.path`;
- роут `app/routers/testcases.py` + схемы (`TestCase`, `TestCasesTree`) в
  `app/schemas.py`, по образцу `sections.py`/`SectionsTree`;
- довесить статус последнего прогона (реюз `_nodeid_to_full_name` +
  `allure_report.parse_results`);
- вкладка в `ui/project.html` + JS-дерево (реюз паттерна дерева разделов);
- фильтр «нет автотеста» не реализуем содержательно — это расхождение с
  требованиями миссии, стоит явно обсудить с владельцем.

## Вариант Б. Своя таблица `test_cases` в `workspace/test_hub.db`

**Источник истины** — сама таблица `test_cases` в test_hub, наполняемая
импортом черновиков и/или ручными правками. Test IT (если синк включат) —
производная копия, не первоисточник.

**Поток данных.**
1. Импорт: новый роут/команда читает markdown-черновики
   `docs/test_cases/*.md` проекта автотестов тем же парсером, что уже есть в
   `testit_sync.py::parse_area_file` (или напрямую запускает
   `tools/test_cases/generate.py` в venv проекта — тот же паттерн, что
   `runner.py` уже использует для запуска pytest в чужом venv), и делает upsert
   в `test_cases` по ключу `(project, nodeid)`.
2. GET `/api/projects/{name}/testcases` читает `test_cases`, строит дерево по
   `section` (тот же `area`/`kind`, что у `sections.py`), довешивает статус
   последнего прогона тем же способом, что в варианте А.
3. UI — вкладка с деревом слева, карточкой кейса справа, кейс редактируется
   прямо в test_hub.

**Правка кейса** — `PUT /api/projects/{name}/testcases/{id}` в UI, роль `qa`
(по аналогии с правкой `issue_url`/`note` у xfail — `manager`/`customer`
только читают). При первой ручной правке `source` кейса переключается
`generated → manual` — тем же приёмом, что `xfail_registry.recalc()` не
затирает `issue_url`/`note` при пересчёте: повторный импорт черновика не
должен переписывать вручную отредактированные поля.

**Версионирование** — по прецеденту `xfail_registry` в проекте истории правок
вообще нет ни у одной подобной сущности, только текущее состояние +
`updated_at`/`first_seen`. Значит «из коробки» здесь тоже ничего не будет —
если владельцу нужен откат, это отдельная таблица `test_case_history`
(append-only: id кейса, старое значение, кто и когда поменял), которую в
проекте по этому шаблону ещё никто не делал — придётся проектировать с нуля.

**Переименование автотеста/nodeid** — связь рвётся так же, как у
`xfail_registry` при переименовании теста: старая запись `test_cases` виснет
на nodeid, которого больше нет (осиротевший кейс — можно показывать в UI как
кейс без автотеста, это ровно фильтр из миссии), а новый nodeid на следующем
импорте создаёт новую пустую запись без текста кейса. Автоматически связь не
восстанавливается — нужно либо ручное решение «это тот же кейс, просто
переименовали» (сопоставление по TC-id или по названию), либо фиксировать
разрыв и чинить руками. Это тот же класс проблемы, что и в А, но здесь она
хотя бы видна как «сирота» в UI, а не молча пропадает.

**Объём работы на этап 2**:
- миграция БД: `test_cases(id, project, section, title, steps JSON, expected,
  precondition, priority, nodeid, source, updated_at, updated_by)` в
  `app/db.py::SCHEMA`, опционально `test_case_history`;
- роут импорта черновиков (реюз/портирование парсера `testit_sync.py`);
- CRUD-роут + права ролей (`qa` пишет, `manager`/`customer` читают);
- вкладка UI: дерево + форма редактирования карточки;
- статус последнего прогона (полный реюз логики из А).

## Вариант В. Test IT как источник истины, test_hub кэширует через API

**Источник истины** — Test IT (проект «ВШГУ v.3»), test_hub только читает и
кэширует у себя `test_cases_cache`.

**Поток данных.**
1. Синхронизация (по кнопке «Обновить из Test IT» или по расписанию, аналогично
   `schedules`) дёргает Test IT Public API v2: `POST /api/v2/workItems/search`
   по секциям проекта, ответ (title/steps/priority/tags) сохраняется в кэш;
   связь с nodeid берётся из тега `autotest:<nodeid>` — того же тега, что уже
   льёт `testit_sync.py` (`autotest_tag()`), отдельного поля для этого заводить
   не нужно.
2. GET `/api/projects/{name}/testcases` читает кэш, строит дерево, довешивает
   статус последнего прогона так же, как в А/Б.

**Правка кейса** — только в самом Test IT (внешний UI), test_hub кнопки
редактирования либо не имеет вовсе, либо делает write-through (PUT сразу шлёт
в Test IT API, кэш обновляется по ответу) — но тогда test_hub должен постоянно
держать `PrivateToken` с правом записи в чужую систему, а не только на чтение.
Сейчас test_hub вообще не хранит секретов с правом записи во внешние системы
(`TESTIT_TOKEN` есть только в `.env` `auto_tests_vshgu_cloude`, не в test_hub).

**Версионирование** — историю ведёт сам Test IT (это его типовая фича для work
item), test_hub её не хранит и не показывает без отдельного API-вызова; текст
миссии эндпоинт истории не упоминает — нужно уточнять по Swagger конкретного
инстанса, есть ли он вообще в Public API v2.

**Переименование автотеста/nodeid** — привязка живёт в теге
`autotest:<nodeid>` внутри Test IT. При переименовании test_hub на следующей
синхронизации видит: nodeid из `sections.py` не находит тега в кэше → кейс
«без автотеста»; новый nodeid — «без кейса». Починка возможна только через
Test IT (кто-то должен поправить тег там), а не в test_hub — то есть разрыв
тот же, что в Б, но лечится в другой системе руками, а не в UI test_hub.

**Объём работы на этап 2**:
- новые секреты в `.env` test_hub: `TESTIT_URL`, `TESTIT_TOKEN`,
  `TESTIT_PROJECT_ID` (сейчас их там нет);
- клиент Test IT в `app/core` (портирование `TestItClient` из
  `testit_sync.py`: `sections`/`workItems/search`);
- таблица кэша + пересчёт по кнопке/расписанию;
- роут чтения + вкладка UI без формы редактирования (или с write-through,
  см. выше — отдельное архитектурное решение);
- обработка состояния «ключ ещё не выдан» — что показывать в UI, пока
  владелец не передал токен.

## Рекомендация

**Вариант Б, с последующим синком в Test IT как отдельным шагом, а не
одновременно.** Основание — факты, а не ожидание из миссии:

1. У test_hub уже есть ровно такой прецедент («второй источник истины поверх
   allure, ручные правки не теряются при пересчёте») — `xfail_registry`. Б
   ложится на этот же шаблон один в один, В — нет ни одного похожего
   прецедента (test_hub нигде не хранит ключей с правом записи во внешние
   системы).
2. В `auto_tests_vshgu_cloude` уже готов весь путь «allure → markdown-черновик
   (`generate.py`) → Test IT (`testit_sync.py`)». Если test_hub сразу пойдёт в
   вариант В (читать из Test IT), markdown-черновики останутся «слепым
   пятном»: и генератор, и синк продолжат жить в другом репозитории, о
   котором test_hub ничего не знает, а сам markdown перестанет быть кому-то
   нужен, хотя он и есть самый дешёвый и уже работающий формат.
3. Б даёт то же самое, что нужно уже сейчас (быстрое чтение/правка в своей
   БД, дерево по разделам, статус прогона), не требуя от владельца немедленно
   выдавать `TESTIT_TOKEN` и решать вопрос прав записи в чужую систему — эти
   вопросы можно отложить до момента, когда решится, нужен ли B поверх Б.
4. В как read-only кэш можно добавить позже вторым шагом поверх Б (кнопка
   «синхронизировать с Test IT» дёргает существующий `testit_sync.py`,
   test_hub получает обратно id заливки) — то есть В не альтернатива Б, а
   вероятный следующий шаг после него.

## Что нужно от владельца, чтобы начать этап 2

- Подтвердить модель прав: `qa` правит кейсы, `manager`/`customer` только
  читают (как в xfail) — или нужна отдельная роль/подтверждение правки.
- Подтвердить источник черновика на первом шаге: импорт из
  `docs/test_cases/*.md` (`auto_tests_vshgu_cloude`) — или test_hub должен
  сам гонять ast-анализ по образцу `generate.py` (тогда нужен доступ к venv
  проекта для `pytest --collect-only`, как у `runner.py`).
- Решение, что делать с кейсами без автотеста (миссия просит фильтр «нет
  автотеста» — по прецеденту `achievements_cases.py` такие кейсы уже
  встречаются) — заводить их вручную в test_hub, или это только для тех,
  что уже есть в Test IT/markdown.
- Если всё-таки сразу нужен синк с Test IT (не откладывать на второй шаг):
  `TESTIT_URL`/`TESTIT_TOKEN`/`TESTIT_PROJECT_ID` и подтверждение точного
  id/имени проекта «ВШГУ v.3» в конкретном инстансе Test IT.
