# Итоговый отчёт: вкладка «Тест-кейсы», этап 1

Отчёт владельцу по миссии `docs/missions/2026-09-29_testcases_tab.md`. Код `app/`/`ui/`
в этой миссии не менялся, стенды и Test IT не вызывались.

## 1. Рекомендация по хранению

Полное обоснование — `docs/missions/testcases/storage_options.md` (3 варианта: А — генерация
на лету из кода тестов, Б — своя таблица `test_cases` в `workspace/test_hub.db`, В — Test IT
как источник истины с кэшем в test_hub). Здесь — только вывод.

**Рекомендован вариант Б: своя таблица `test_cases`, синк в Test IT — отдельным шагом позже,
не одновременно.** Три ключевых аргумента:

1. В test_hub уже есть готовый прецедент ровно под эту задачу — `xfail_registry`
   (`app/core/xfail_registry.py`): второй источник истины поверх allure, ручные правки
   (`issue_url`/`note`) не затираются при автоматическом пересчёте. Вариант Б ложится на этот
   шаблон один в один; у варианта В такого прецедента нет — test_hub нигде не хранит ключей
   с правом записи во внешние системы.
2. В `auto_tests_vshgu_cloude` уже работает конвейер «allure → markdown-черновик
   (`tools/test_cases/generate.py`) → Test IT (`tools/test_cases/testit_sync.py`)». Если сразу
   выбрать вариант В, этот готовый и дешёвый путь останется невостребованным.
3. Б не требует от владельца немедленно выдавать `TESTIT_TOKEN` и решать вопрос прав записи
   в чужую систему — эти вопросы откладываются до решения, нужен ли поверх Б ещё и В
   (read-only кэш из Test IT можно добавить вторым шагом, не переделывая Б).

Вариант А отклонён отдельно: он не даёт кейсов без автотеста и ручных правок, а фильтр
«нет автотеста» из требований миссии в нём принципиально пустой.

## 2. Что понадобится на этапе 2 (если владелец согласится с рекомендацией)

- **Миграция БД** — новая таблица в `app/db.py::SCHEMA`:
  `test_cases(id, project, section, title, steps JSON, expected, precondition, priority,
  nodeid, source, updated_at, updated_by)`. По образцу `xfail_registry` источник (`source`)
  переключается `generated → manual` при первой ручной правке, чтобы повторный импорт
  черновика её не затирал.
- **API-роуты** в test_hub, по образцу `app/routers/xfail.py`:
  - `GET /api/projects/{name}/testcases` — дерево кейсов по разделам (реюз структуры
    `sections.py`) со статусом последнего прогона автотеста (nodeid → fullName →
    `allure_report.parse_results`, тем же приёмом, что уже в `flaky`/`coverage`/
    `xfail_registry`);
  - `PUT /api/projects/{name}/testcases/{id}` — правка кейса;
  - роут/команда импорта черновиков `docs/test_cases/*.md` из `auto_tests_vshgu_cloude`
    (парсер уже есть в `testit_sync.py::parse_area_file`, портируется в test_hub).
- **Права ролей.** Сверено с текущей моделью в README.md (раздел про роли, таблица прав) и с
  `app/routers/xfail.py`: `GET .../xfail` — qa/manager/customer, `PUT .../xfail/{id}` — только
  qa. Для `test_cases` предлагается та же схема: `GET` читают qa/manager/customer, `PUT`
  (правка кейса) — только qa. Это не противоречит существующей модели прав в проекте, отдельной
  новой роли заводить не нужно.

## 4. Известные ограничения этапа 1 (незакрытые дефекты)

Из QA-проверки Дуайта (`docs/missions/testcases/qa_notes.md`), не устранено в рамках этого
отчёта — правка `mockups.html`/скрипта экспорта не входит в задачу этого документа:

- **Обрезан верх во всех 4 экспортированных JPG** (`testcases-tree-dark.jpg`,
  `testcases-tree-light.jpg`, `testcases-table-dark.jpg`, `testcases-table-light.jpg`): не видно
  ни шапки макета с переключателем варианта/темы, ни заголовка `<h2>` конкретного варианта.
  Причина — `.ctl` в `mockups.html` (`position:sticky; top:0; z-index:20`) перекрывает верх
  секции при захвате скриншота Playwright; нужен больший `scroll-margin-top`/отступ кадра в
  скрипте экспорта. Сам `mockups.html` вёрстку содержит верно — дефект только в JPG-экспорте.
  На макет по существу (соответствие вариантов, тем, данных, токенов `DESIGN.md`) дефект не
  влияет.

## 5. Укрупнённая оценка объёма работ этапа 2

Порядок с зависимостями (каждый следующий пункт опирается на предыдущий):

1. Миграция БД: таблица `test_cases` в `app/db.py::SCHEMA`.
2. Импорт черновиков: роут/команда, читающая `docs/test_cases/*.md` из
   `auto_tests_vshgu_cloude` парсером по образцу `testit_sync.py::parse_area_file`, upsert
   в `test_cases` по ключу `(project, nodeid)`.
3. `GET /api/projects/{name}/testcases`: дерево по разделам + статус последнего прогона
   (реюз `_nodeid_to_full_name` и `allure_report.parse_results`, как в `xfail_registry`).
4. `PUT /api/projects/{name}/testcases/{id}`: правка кейса, роль `qa`, с переключением
   `source: generated → manual`.
5. Вкладка «Тест-кейсы» в `ui/project.html` + JS: один из двух макетов (или оба —
   переключатель, как в `mockups.html`) поверх готовых роутов пп. 3–4.
6. (Отдельным шагом позже, не в этом же этапе) — синк с Test IT как read-only кэш поверх
   готовой таблицы `test_cases`, если владелец решит, что он нужен.

Пп. 1–2 можно начинать сразу, п. 3 зависит от п. 1, пп. 4–5 — от п. 3.
