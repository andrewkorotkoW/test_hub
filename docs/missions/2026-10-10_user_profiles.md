# Миссия: профиль пользователя, регистрация с одобрением, аватар в шапке

Записано 10.10.2026 по запросу владельца (скриншот страницы «Проекты», стрелка на бейдж
роли в шапке справа — сейчас там просто текст `admin SUPERADMIN`). Идея: отдельная страница
профиля (ФИО, должность, проект, в котором пользователь задействован), форма регистрации с
одобрением, на главной странице — аватар вместо/рядом с текстовым бейджем роли, клик по
аватару → страница профиля.

Решения по неуточнённым владельцем деталям (чтобы не блокироваться — можно поправить после
показа):
- Одобряет **qa или superadmin** — та же роль, что уже управляет пользователями в
  `admin.html` («Стенды и пользователи», `app/routers/users.py`, `require_roles("qa")`,
  superadmin проходит через любой `require_roles` автоматически, см. `app/deps.py`).
- «Проект, где задействован» — **выпадающий список из уже существующих проектов**
  (`SELECT name FROM projects`), не свободный текст — так пользователь профиля сразу
  сопоставим с данными, которые уже знает система, без опечаток.
- Аватар — **загрузка PNG/JPG** (как у вложений тест-кейсов, `TH_TESTCASE_ATTACHMENT_MAX_BYTES`
  в `app/core/test_cases.py` — тот же лимит и проверка типа), без аватара — кружок с
  инициалами, как уже сделано для логотипов проектов (`ui/projects.js`, `.logo-placeholder`).

## Что уже есть (не переделывать)

- `users` таблица: `login TEXT PRIMARY KEY, password_hash, role CHECK(...), onboarded`.
- `app/routers/auth.py` — `/api/login`, `/api/logout`, `/api/me`, `/api/me/onboarded`.
- `app/routers/users.py` — CRUD пользователей, `require_roles("qa")`, используется
  `admin.html` (раздел «Пользователи», `#user-form`).
- `ui/common.js::renderSidebar` — показывает роль в шапке текстом; здесь добавится аватар.
- Паттерн аватара/логотипа с fallback на инициалы уже есть для проектов
  (`ui/projects.js`, `img/logos/<project>_256.png`, `.logo-placeholder` при ошибке
  загрузки) — повторить тот же приём для пользователя.

## Часть 1 — схема и бэкенд

1. Миграция `users`: добавить `full_name TEXT`, `position TEXT`,
   `project TEXT REFERENCES projects(name)` (nullable), `avatar_filename TEXT` (nullable),
   `status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','pending','rejected'))`.
   Существующие (сидированные) пользователи — `status='active'` по умолчанию, ничего не
   меняется в их поведении.
2. `POST /api/auth/register` (публичный, без авторизации) — `login`, `password`, `full_name`,
   `position`, `project` (опционально) → создаёт пользователя с `status='pending'`,
   `role='customer'` (минимальная роль по умолчанию, меняется при одобрении). Без установки
   сессионной куки — пользователь ещё не может войти.
3. `POST /api/login` — если `status != 'active'`, отдавать `403` с понятным сообщением
   («Заявка ещё не одобрена» / «Заявка отклонена»), не `401 Invalid credentials` (пароль-то
   верный).
4. `PUT /api/users/{login}/approve` (`require_roles("qa")`) — принимает опционально `role` в
   теле (если не передан — оставить `customer`), ставит `status='active'`.
5. `PUT /api/users/{login}/reject` (`require_roles("qa")`) — `status='rejected'` (не удалять
   — так остаётся след для разбора, как soft delete у курсов/площадок в других проектах).
6. `GET /api/me` / `GET /api/users` — расширить payload: `full_name`, `position`, `project`,
   `status`, `avatar_url` (например `/api/me/avatar` или `null`, если аватара нет).
7. `PUT /api/me` (любой активный пользователь, `get_current_user`) — редактирует свои
   `full_name`/`position`/`project` (не `role`/`login`/`status` — это не самообслуживание).
8. `POST /api/me/avatar` (multipart, PNG/JPG, лимит как у `TH_TESTCASE_ATTACHMENT_MAX_BYTES`)
   — сохраняет файл (например `workspace/avatars/<login>.<ext>`), обновляет
   `avatar_filename`. `GET /api/me/avatar` / `GET /api/users/{login}/avatar` — отдаёт файл.

## Часть 2 — страница профиля и регистрация

- `ui/profile.html`+`profile.js` — своя ФИО/должность/проект (редактируемые поля, `PUT
  /api/me`), загрузка аватара, в том же визуальном стиле, что остальные страницы (сайдбар
  через `common.js`).
- `ui/register.html`+`register.js` — публичная форма (без сайдбара/логина): логин, пароль,
  ФИО, должность, проект (select из `GET /api/projects` — публичный ли этот список или нужен
  отдельный облегчённый эндпоинт без авторизации для одних только имён проектов, решить по
  месту). После отправки — экран «Заявка отправлена, ждите одобрения», без автовхода.
- `ui/index.html` (страница логина) — ссылка «Нет аккаунта? Зарегистрироваться» →
  `register.html`; при логине с `403` от сервера (п.3) — показать текст ошибки сервера как
  есть, не универсальное «неверный логin/пароль».

## Часть 3 — аватар в шапке и одобрение заявок

- `ui/common.js` — в шапке (там, где сейчас `admin <ROLE>` текстом) добавить кружок-аватар
  (картинка или инициалы по фолбэку `.logo-placeholder`, тот же приём, что у логотипов
  проектов), клик → `profile.html`. Роль можно оставить рядом текстом или перенести в
  тултип/профиль — на усмотрение исполнителя, не критично.
- `ui/admin.html` раздел «Пользователи» — добавить колонки ФИО/Должность/Проект/Статус в
  существующую таблицу; отдельный под-список «Заявки на регистрацию» (пользователи
  `status='pending'`) с кнопками «Одобрить»/«Отклонить» (одобрение — с выбором роли тут же).

## Правила

- Не трогать существующих сидированных пользователей (qa/manager/customer/admin,
  `status='active'` по умолчанию через `DEFAULT`, не через ручной UPDATE).
- Коммиты без Co-Authored-By трейлера.
- После смены бэкенда — перезапуск сервера (`launchctl kickstart -k
  gui/$(id -u)/su.andrey.test_hub`), перед этим убедиться, что нет идущего прогона.
