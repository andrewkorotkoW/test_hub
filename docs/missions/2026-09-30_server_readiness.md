# Миссия: test_hub переезжает на сервер — готовность к развёртыванию

Записано 30.09.2026: владелец сообщил, что проект переезжает на сервер. Сейчас test_hub живёт на
macOS владельца под launchd с абсолютными путями `/Users/andreykorotkow/...`. Нужно, чтобы тот же
код поднимался на Linux-сервере одной командой, без ручных правок.

## Что должно получиться

1. **Никаких абсолютных путей владельца в коде.** `app/db.py` (SEED_PROJECTS, VSHGU_PROJECT_PATH,
   Demo), `app/config.py`, тесты — пути проектов только из `.env` (`TH_PROJECTS_ROOT`,
   `TH_VSHGU_PATH` и т.п.) или из БД; сид VSHGU/bike_fit/Velo_bot — только если путь существует
   (уже так), Demo — всегда. Тесты, которые ссылаются на `/Users/...`, переписать на фикстурные пути.
2. **Docker**: `Dockerfile` (python 3.11-slim, Playwright с браузерами для UI-тестов проектов,
   Java + allure CLI, `TH_ALLURE_BIN` внутри образа), `docker-compose.yml` (сервис test_hub, том для
   `workspace/`, том/монтирование репозиториев тестов, порт, `.env`). Проекты тестов внутри
   контейнера: путь `/projects/<repo>` + свои `.venv` — описать, как их создавать (`setup.sh`
   внутри контейнера или отдельный образ на проект — выбрать и обосновать в отчёте).
3. **Без Docker**: `deploy/test_hub.service` (systemd unit) + `deploy/install.sh` для Ubuntu
   (python, venv, playwright install-deps, allure), обновление `git pull && restart`.
4. **Публичность**: `TH_PUBLIC_URL` для ссылок «Поделиться» и бота; пример конфига nginx с HTTPS
   (`deploy/nginx.conf.example`) и WebSocket (`/ws/runs/`); `TH_SECRET` обязателен не по умолчанию —
   при `change-me` в продовом режиме (`TH_ENV=prod`) сервер отказывается стартовать с понятной ошибкой;
   пароли seed-пользователей qa/qa, admin/admin — при `TH_ENV=prod` принудительная смена при первом
   входе или генерация случайных с выводом в лог один раз.
5. **Данные**: `workspace/` целиком переносимый (БД, allure-results, frames, testcases, coverage);
   скрипт `deploy/migrate_workspace.sh` для переноса с мака на сервер (rsync + проверка целостности БД);
   бэкап БД по cron (`deploy/backup.sh`).
6. **Cron и планировщик**: расписания прогонов и автосводки работают внутри одного процесса —
   проверить, что после перезапуска контейнера ничего не дублируется; Telegram-бот test_hub —
   токен из `.env`.
7. **Документация**: `docs/DEPLOY.md` — пошагово: сервер с нуля (Docker и без), перенос workspace,
   подключение проектов тестов (клон репозиториев на сервер, `.env` проектов, venv, Playwright),
   обновление, откат, где логи. README — ссылка на него.
8. **Тесты**: конфиг путей, отказ старта с `change-me` в prod, миграция workspace на фикстуре;
   существующие тесты проходят; сборка Docker-образа проверяется хотя бы `docker build`
   (если docker недоступен в среде агента — написать в отчёте, что не проверено).

## Ограничения

- Ничего не ломать для текущей установки владельца на macOS: launchd-запуск продолжает работать,
  `.env` владельца не трогать (новые переменные — с дефолтами, совпадающими с нынешним поведением).
- Секреты и токены — только через `.env`, в репозиторий не попадают.
- Коммиты небольшие, на русском.

## Что нужно от владельца (заполнить, когда узнаем)

- ОС и доступ к серверу (ssh), домен/адрес, есть ли Docker, кто выдаёт HTTPS-сертификат.
- Где будут лежать репозитории тестов на сервере и доступ к GitLab с сервера (deploy key).
- Нужен ли доступ с сервера к стендам develop/stage (VPN/белые списки).
