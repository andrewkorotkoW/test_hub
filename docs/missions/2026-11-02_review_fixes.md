# Миссия: пять правок по итогам ревью всех страниц (02.11.2026)

Записано 02.11.2026 по итогам обхода всех 16 страниц test_hub под ролью qa (проект VSHGU).
Общий вывод ревью: продукт целостный, главный риск — доверие к цифрам на первом экране.
Пять пунктов ниже — самые заметные; все они небольшие, не трогают контракт плагина
(`utils/test_hub_plugin.py` в проекте тестов), CI и схему покрытия.

Общие правила: ветка от `main`, `pytest -q` зелёный (известный флак
`tests/test_runner_timeout.py` не считать), чистая логика без DOM — в `ui/*-logic.js`
с тестом через node (node v12: без `??`/`?.`), README — абзац на каждый пункт.
Отчёт — `docs/reports/2026-11-02_review_fixes.md`.

## 1. Дашборд и статистика не берут отменённый прогон за «последний»

**Факт.** 02.11 дашборд VSHGU показывал «% passed 4.3 %, упало 159» красным по прогону
#115 — он `cancelled`, и 113 из 159 падений классифицированы как `session` (стенд
потерял сессию), 6 — `stand`, кода — 10. Отменённый прогон по определению неполный,
а ещё и упавший по стенду, — на него нельзя опираться как на состояние проекта.

**Где.** `app/core/stats.py::_latest_full_run` и `latest_finished_run_id` выбирают
`status IN ('passed', 'failed', 'cancelled')`; `FINISHED_STATUSES` там же. Дашборд
(`ui/project-dashboard.js`, KPI и «Статусы последнего прогона», `sourceRun`) и страница
«Статистика» (`app/routers/stats.py`) идут через них.

**Что сделать.**
- Для KPI/«последний прогон» — только `passed`/`failed`. `cancelled` остаётся в динамике
  (30-дневные графики) и в ленте, но не в «последнем прогоне».
- Подпись источника на плитках KPI и у кольца «Статусы последнего прогона»:
  «по прогону #N · стенд · дата» (ссылка на окно прогона). Сейчас цифры «Всего тестов 185»
  у проекта на 686 тестов ничем не объяснены.
- Если у последнего прогона инфраструктурных причин (`throttling`/`session`/`stand`,
  см. `app/core/failure_causes.py`) больше половины падений — пометка «стенд, не код»
  рядом с «% passed», тем же бейджем, что в ленте («· 119 стенд»).
- Тесты: прогон `cancelled` новее `failed` → KPI по `failed`; подпись содержит id/стенд;
  бейдж появляется при доле инфраструктурных причин > 50 %.

## 2. «Статистика» без полного прогона на стенде

**Факт.** Для стенда 2066 страница показывает таблицу разделов целиком в нулях и красный
блок «Разделы без единого теста» из 55 пунктов — все разделы проекта. Причина: на 2066
не было прогона с `target = 'all'`, а раздел считается «по последнему полному прогону»
(`_latest_full_run`). Выглядит как сломанная страница, а не как «данных нет».

**Где.** `app/core/stats.py` (`_latest_full_run`, расчёт разделов), `app/routers/stats.py`,
`ui/stats.js` (`topSlowestList` и блок «Разделы без единого теста»).

**Что сделать.**
- Нет полного прогона на стенде → вместо таблицы нулей одно состояние: «Полного прогона
  на стенде <имя> не было. Последний прогон — #N (<цель>, дата)» с кнопкой «Показать по
  последнему прогону» (считает по нему, с пометкой «частичный прогон, N из M тестов»).
- Блок «Разделы без единого теста» показывать только когда есть полный прогон; при
  частичном — не показывать вовсе (список разделов, которых просто не было в цели, —
  не «без тестов»).
- Тесты: стенд без `all`-прогонов → ответ API с полем `full_run: null` и `fallback_run`;
  UI рисует состояние, а не таблицу.

## 3. Сплит окна прогона — те же финальные попытки, что и счётчики

**Факт.** Прогон #105: счётчики 51/2/1/3 = 57 тестов (после `final_attempts`), а список
«Тесты» в сплите — 72 строки: `TestActivityLaunchFlow::test_activity_launch` дважды под
FAILED, `test_user_gets_achievement_by_material[article]` четыре раза под PASSED. Это
реран (`flaky(reruns=1)` в conftest проекта) плюс повторы из событий — то, что для
счётчиков уже починено 22.10 (`allure_report.final_attempts`), в списке не применено.

**Где.** `app/routers/runs.py::list_run_tests` — ветка после завершения прогона берёт
`allure_report.parse_results(...)` напрямую (строка ~65 функции), без `final_attempts`;
ветка во время прогона собирает по `run_events` `test_start`/`test_end`.

**Что сделать.**
- После завершения: `final_attempts(results, row["repeat"])`; у записи отдавать
  `attempts` и показывать в сплите пометку «прошёл со 2-й попытки» (если `attempts > 1`
  и финальный статус `passed`) — это полезный сигнал нестабильности, не шум.
- Во время прогона: по одному nodeid — одна строка, статус последнего `test_end`.
- Заголовок «Тесты N» должен совпадать с суммой счётчиков в шапке.
- Тесты: allure с двумя попытками одного теста → одна строка со статусом последней и
  `attempts: 2`; `repeat > 1` — все записи, как в `final_attempts`.

## 4. Флаки: ноль падений при высокой нестабильности

**Факт.** В таблице флаки: `test_get_course_row_filters_by_stream_id` — 4 запуска,
0 падений, 67 %; `test_view_applicant_card` — 5, 0, 50 %. Для qa это выглядит ошибкой:
«ни разу не упал, но нестабилен».

**Где.** `app/core/flaky.py::recalc`: `fails` считает `failed`/`broken` только с причиной
`None`/`code`, а `flips` — смены эффективного статуса, куда попадают и `broken` с
инфраструктурной причиной (унаследованный `prev`), и `skipped`, и переходы
`passed → skipped → passed` через наследование. Расхождение заложено в самой паре метрик.

**Что сделать.**
- Считать `flips` по тому же набору, что и `fails`: смена статуса учитывается только
  между «настоящими» результатами (`passed` и падения с причиной `code`/`None`);
  инфраструктурные падения и `skipped` из последовательности исключаются, а не
  наследуются. Тогда `fails = 0` ⇒ `flips = 0` ⇒ `score = 0`.
- В таблице добавить колонку «из них стенд» (падения с инфраструктурной причиной), чтобы
  было видно, почему тест в списке пришёл и ушёл.
- Подпись к «% нестабильности» (title): «доля смен passed↔failed между соседними
  прогонами, стендовые падения не считаются».
- Тесты: последовательность `passed, broken(stand), passed` → fails 0, flips 0;
  `passed, failed(code), passed` → fails 1, flips 2, score 100 %;
  `passed, skipped, failed(code)` → fails 1, flips 1.

## 5. Ретеншен результатов на диске

**Факт.** `workspace/runs` (видео) 1.9 ГБ, `allure-results` 1.4 ГБ, `allure-reports`
0.5 ГБ, `frames` 0.45 ГБ — 4.3 ГБ, +1 ГБ за две недели. Удаление есть только вручную в
суперадминке (`app/routers/admin.py`, `shutil.rmtree` по прогону).

**Где.** `app/config.py` (настройки), `app/core/runner.py` (`allure_dir`, `frames_dir`,
`video_dir`), `app/core/allure_report.py` (сгенерированные отчёты), `app/main.py::lifespan`
(фоновые задачи, как `scheduler_loop`), `app/routers/admin.py` (ручное удаление).

**Что сделать.**
- Настройки в `.env` с дефолтами: `TH_KEEP_VIDEO_DAYS=14`, `TH_KEEP_FRAMES_DAYS=30`,
  `TH_KEEP_RESULTS_DAYS=90`, `TH_KEEP_REPORTS_DAYS=30`. `0` — не удалять. Добавить в
  `.env.example` и README.
- Фоновая задача раз в сутки (в `lifespan`, по образцу `scheduler_loop`): по `runs.finished`
  удалять видео/кадры/результаты/отчёты старше порога. Запись прогона, `counts`,
  `run_test_results`, `run_events` — остаются навсегда: история, Δ и флаки от файлов
  не зависят (флаки читает allure с диска — `flaky.recalc` должен пропускать прогоны без
  каталога, проверить).
- Не удалять файлы прогонов, на которые есть живая публичная ссылка
  (`share_links` без `revoked`, `expires_at` в будущем) — продлить до истечения ссылки.
- В окне прогона, если видео/кадры удалены по сроку — «удалено по сроку хранения (N дней)»
  вместо «Плагин не записал видео».
- Суперадминка: строка «Диск: видео X ГБ, результаты Y ГБ…» и кнопка «Очистить сейчас».
- Тесты: прогон старше порога → каталоги удалены, строка в `runs` цела; прогон с живой
  share-ссылкой → не тронут; `0` — ничего не удаляется.

## Что не входит

- Четыре процента покрытия на одном экране, чёрный блок видео в светлой теме, удалённые
  стенды в фильтре истории, пункт «Sentry» в сайдбаре — отдельно, после этой миссии.
