# Миссия: вкладка «Тест-кейсы» на странице проекта. Этап 1 — где хранить данные и макет

Записано 29.09.2026 по просьбе владельца. Открытый вопрос владельца: **где хранить тест-кейсы**.
Решение по хранению принимает владелец после этого этапа, код test_hub (`app/`, `ui/`) в этой
миссии не менять.

## Что хочет владелец

На странице проекта (`ui/project.html`, вкладки Дашборд/Запуск/Расписания/История/Флаки) —
новая вкладка **«Тест-кейсы»**: список кейсов проекта по разделам (как дерево `sections`),
у кейса — название, шаги, ожидаемый результат, приоритет, связь с автотестом (nodeid) и
статус последнего прогона этого автотеста, если он есть. Поиск и фильтр по разделу/статусу
(есть автотест / нет автотеста / падает).

## Что есть сейчас (изучить, не выдумывать)

- В проекте автотестов `auto_tests_vshgu_cloude` уже есть генератор черновиков кейсов из
  allure-результатов и скрипт синхронизации с Test IT (проект «ВШГУ v.3»): найти в репозитории
  по словам `testit`, `cases`, `allure` (папки `tools/`, `scripts/`, `docs/`), прочитать формат
  черновика (название, шаги из `allure.step`, предусловия, приоритет).
- test_hub знает дерево разделов (`app/core/sections.py`), результаты прогонов
  (`runs.counts`, allure-результаты прогона в `workspace/`), покрытие (`app/core/coverage.py`),
  флаки и известные дефекты (`xfail_registry`).
- Test IT: публичное API v2 (`PrivateToken`, `POST /api/v2/workItems/search`, `workItems/{id}`);
  ключ — в `.env` владельца, в миссии его не использовать, только описать.

## Этап 1 (эта миссия)

1. **Записка по хранению** `docs/missions/testcases/storage_options.md` — 3 варианта, по каждому:
   что источник истины, как попадают данные, как правится кейс, что с версионированием,
   что ломается при переименовании теста, сколько работы. Кандидаты:
   - А. **Генерировать на лету** из кода тестов/allure (docstring, `allure.title`, `allure.step`),
     ничего не хранить: кейс = автотест. Плюс: всегда актуально. Минус: нет кейсов без автотеста
     и ручных правок.
   - Б. **Своя таблица в `workspace/test_hub.db`** (`test_cases`: project, section, title, steps
     JSON, expected, priority, nodeid, source, updated_at) + импорт черновиков из allure/генератора,
     правка в UI. Плюс: свои данные, быстро. Минус: второй источник истины рядом с Test IT.
   - В. **Test IT как источник истины**, test_hub читает через API и кэширует в БД
     (workItems по секциям проекта), связь с автотестом по полю/тегу nodeid, правки только в Test IT.
     Плюс: одна база кейсов для всех. Минус: зависимость от внешней системы и ключа.
   - Дать рекомендацию с обоснованием (ожидается Б с экспортом/синком в Test IT или В с кэшем,
     но решать по фактам), и что нужно от владельца, чтобы начать этап 2.
2. **Макет вкладки** `docs/missions/testcases/mockups.html` — 2 варианта вкладки «Тест-кейсы»
   (список по дереву разделов с карточкой кейса справа; таблица с раскрывающимися шагами),
   светлая и тёмная тема, токены из `DESIGN.md`, данные — реальные кейсы из генератора черновиков
   проекта автотестов (взять 20–30 кейсов из 3–4 разделов). Экспорт в JPG 1440 px, обе темы,
   Playwright из `.venv`.
3. В отчёте: рекомендация по хранению, что понадобится (миграция БД, роут API, права ролей:
   qa правит, manager/customer читают), оценка этапа 2.
