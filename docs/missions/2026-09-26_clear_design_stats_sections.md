# Миссия: чёткий макет страниц, статистика по дашбордам, запуск тестов по разделам

Записано 26.09.2026 по просьбе владельца. Три части, порядок важен: макет → статистика → запуск
по разделам. Выполняется после миссии «редизайн страниц» (2026-09-24): не переписывать то, что
она сдаёт, а строить поверх. Источник токенов — `DESIGN.md`; референсы — `docs/missions/REFERENCES.md`
и `docs/missions/redesign/`.

## Часть 1. Более чёткий макет (сначала показать, потом делать)

Владелец посмотрел четыре варианта (`redesign/variants/`) и хочет **более чёткий**: меньше
декоративного, больше читаемости и иерархии. Ориентиры чёткости:
- один акцентный цвет на экран (цвет проекта), статусы — только семантические цвета, градиенты
  только в графиках и не больше одного на экран;
- крупные цифры KPI и подписи к ним, всё остальное второстепенное и тише;
- сетка 12 колонок с постоянными отступами, карточки одного размера в ряду, никаких «bento»
  с разными высотами;
- таблицы с чёткими заголовками, зеброй строк и фиксированной шапкой при прокрутке;
- контраст текста не ниже AA в обеих темах, шрифт не меньше 12px.

Задача 1 (макет): сделать **два** варианта макета страниц `projects.html`, `project.html`,
`coverage.html` — как `redesign/variants/mockups.html` (один HTML-файл с переключателем вариантов и
тем, на реальных данных из БД test_hub), PNG-скриншоты каждой страницы в обеих темах в
`docs/missions/redesign/v2/`. Сдать на ревью **без реализации в UI** — владелец выберет вариант
(его выбор придёт заметкой к следующей задаче; без заметки брать вариант A).

Задача 2 (реализация): перестроить `projects.html`, `project.html`, `coverage.html` по выбранному
варианту, переиспользуя готовые виджеты (KPI, кольцо, столбцы, treemap, лента). Скриншоты
до/после в `docs/screenshots/`.

## Часть 2. Статистика по дашбордам

Новая страница `stats.html` (пункт меню «Статистика») и API `GET /api/projects/{name}/stats`:
- **по разделам** (области = папки `tests/api/<area>`, `tests/ui/<area>`, `tests/e2e`): число
  тестов, passed/failed/xfail/skipped в последнем полном прогоне, доля passed, средняя
  длительность раздела, флаки и xfail по разделу, покрытие маршрутов по разделу (из coverage);
- **динамика**: доля passed и длительность по прогонам за 30 дней, по проекту и по разделу
  (выбор раздела в фильтре); графики — площадной и столбцы, как на дашборде проекта;
- **топы**: 10 самых долгих тестов, 10 самых нестабильных, разделы без единого теста;
- выгрузка таблицы разделов в CSV.
Данные брать из `runs`, `run_events`/allure-results, `flaky_stats`, `xfail_registry`,
`workspace/coverage/<project>/coverage.json`; считать на бэкенде, кэшировать по id последнего
прогона. Бот: `/stats <проект>` — краткая сводка по разделам текстом.

## Часть 3. Запуск тестов по разделам

- В форме запуска (`project.html`, кнопка «Запустить прогон») вместо ручного `target`:
  дерево разделов с чекбоксами (api / ui / e2e → области → файлы), поиск по названию,
  быстрые пресеты «API», «UI», «smoke», «всё»; выбранные пути превращаются в `target`
  (через перевод строки, как принимает runner), ручное поле остаётся под спойлером.
- Дерево разделов отдаёт API `GET /api/projects/{name}/sections` (сканирование `tests/` без
  запуска pytest, кэш по mtime); в дереве рядом с разделом — число тестов и статус последнего
  прогона этого раздела (из части 2).
- Бот: `/run <проект> <раздел>` (например `/run auto_tests_vshgu_cloude api/notifications`) с
  подтверждением; stage по-прежнему только по явной команде владельца (см. миссию manual_only).
- Расписания: в форме расписания тот же выбор разделов.

## Ограничения

- Стенды не трогать; прогоны для проверки — только локальные тестовые репозитории/фикстуры.
- Существующие тесты проходят; новые тесты на API stats/sections и на чистые функции UI
  (агрегация по разделам, сборка target из дерева).
