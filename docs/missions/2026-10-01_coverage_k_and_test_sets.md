# Миссия: покрытие в варианте K (Панель + Светофор) и «сборки тестов» с отдельной страницей запуска

Записано 01.10.2026 по решению владельца. Макет утверждён: `docs/missions/redesign/coverage_v6/`
(`mockups.html`, `coverage-k-panel-traffic-dark.jpg` / `-light.jpg`). Макет собран из варианта D
(`coverage_v2`, шапка: KPI-плитки и ряд колец) и варианта G (`coverage_v3`, три колонки светофора).
Токены и стили — только из `DESIGN.md`, макет их уже использует: переносить CSS оттуда.

## Правила

- Схему продукта v5 (`ui/coverage.html` сейчас) **не удалять**: она остаётся вторым видом
  страницы «Покрытие», переключатель «Светофор | Схема» в шапке карточки (как выбор стенда).
  По умолчанию открывается «Светофор». Выбор запоминать в localStorage.
- Данные — только реальные, из существующих API (`GET /api/projects/{name}/coverage`,
  `/coverage/tree`, `runner.discover`, статусы последнего прогона по стенду). Никаких снимков
  из docs/missions в коде.
- Роли как у страницы покрытия сейчас (qa/manager/customer читают; запуск — qa/manager, как в
  форме запуска). Тесты на API и на разбор данных, UI-логика — в отдельных `*-logic.js`
  модулях с unit-тестами по образцу `ui/coverage-areas-logic.js`.
- Сервер после merge перезапускает владелец (launchd). Прогоны на стендах не запускать.

## Этап 1. Страница «Покрытие»: вид «Светофор» (вариант K)

1. **Шапка KPI** (4 плитки): «Страниц покрыто N / M» и «Маршрутов покрыто N / M» — из
   инвентаря покрытия (`coverage.json`: pages/routes covered/total, как в `coverage_v2/collect_data.py`);
   gauge «% покрытия (маршруты + страницы)»; «Областей без тестов N / M» — области маршрутов без
   единого покрытого. Если инвентаря маршрутов у проекта нет (Demo, Courseditor_Learn) — плитки
   маршрутов/областей показывают «нет инвентаря» серым, страница не ломается.
2. **Ряд колец**: API / UI / E2E (доля passed от исполненных на выбранном стенде, число тестов) и
   топ-6 разделов по числу тестов. Цвет кольца: ≥80 % зелёный, ≥50 % жёлтый, ниже красный
   (`pctColor` из макета).
3. **Строка итога + трёхцветная полоса**: «N из M разделов покрыты автотестами — X проходят без
   замечаний, Y требуют внимания, Z совсем без тестов».
4. **Три колонки**: «Покрыто и проходит» (все тесты раздела passed на выбранном стенде),
   «Есть проблемы» (есть failed/broken — красная карточка, идут первыми; иначе xfail/skipped —
   жёлтая), «Не покрыто» (области маршрутов без тестов, серые). **Раздел** = второй уровень
   дерева тестов: `tests/api/<area>` и `tests/ui/<area>` объединяются в один раздел `<area>`
   (подпись — как в дереве покрытия сейчас, русские названия из `coverage-areas-logic.js`
   если есть, иначе имя папки); `tests/e2e` — отдельный раздел «Сквозные сценарии».
   Карточка: точка статуса, название, тег (пройдено/частично/падает/нет тестов), строка
   «N тестов · API a · UI b · E2E c». Колонки прокручиваются внутри, высота как в макете.
5. **Стенд** — тот же селектор, что сейчас; смена стенда пересчитывает всё.
6. **Клик по карточке раздела и по кольцу раздела** → страница сборки (этап 2):
   `project.html?name=<project>&set=<area>#run`. Клик по серой карточке — ничего (нет тестов),
   курсор обычный.
7. Тур (`ui/tour.js`): шаг про покрытие обновить под новый вид.

## Этап 2. «Сборка тестов» — динамическая страница запуска

Сборка = именованный набор тестов (раздел покрытия). У каждой сборки своя страница запуска и
своя история прогонов. Реализация в `ui/project.html`/`project.js` на вкладке «Запуск»:

1. **URL** `project.html?name=<project>&set=<area>#run` открывает вкладку «Запуск» в режиме
   сборки: заголовок «Сборка: <название раздела>», под ним число тестов и состав
   (список файлов/классов из `runner.discover`, свёрнутый по умолчанию), статус последнего
   прогона этой сборки по каждому стенду (точка + дата + passed/failed), кнопка «К покрытию».
   Цели запуска подставлены автоматически: все префиксы раздела (`tests/api/<area>`,
   `tests/ui/<area>`), поле целей скрыто, но доступно по «Изменить состав».
2. **Запуск**: стенд, маркер, повторы — как в обычной форме. `POST /api/projects/{name}/runs`
   получает новое необязательное поле `label` (= имя сборки). Миграция: колонка `runs.label TEXT`
   в `app/db.py` по образцу существующих миграций. Существующие вызовы без `label` работают.
3. **Окно прогона** после старта — то же окно «Сплит» (`docs/missions/2026-09-29_run_window_stage2.md`),
   без изменений; в заголовке окна и в списке прогонов показывать `label`, если есть.
4. **История сборки**: на странице сборки блок «Прогоны этой сборки» — последние 10 прогонов
   с `label = <area>` (стенд, дата, итог, ссылка на прогон и на share, если есть).
   `GET /api/projects/{name}/runs` принимает фильтр `?label=`.
5. **Ссылка на сборку** стабильная: её можно отправить коллеге, у customer/manager она
   открывается в режиме «только просмотр» (состав, история, без кнопки запуска), как и другие
   их ограничения сейчас.
6. **Дайджест / Ральф** (`app/core/digest.py`, telegram): прогон с `label` называть
   «сборка <label>» вместо списка целей — минимальная правка форматирования, если формат
   позволяет; иначе пропустить и написать в отчёте.
7. Демо-проект (`demo/`): сиды прогонов получают `label` у 2–3 прогонов, чтобы новая страница
   была видна в туре и на пустой базе.
