  вкладками «Кадры» (картинка для UI-теста), «Консоль» (вывод pytest по этому тесту) и

- **в · «Терминал»** (`run-c-terminal-{light,dark}.jpg`) — консоль на весь блок как

## Каких данных сейчас нет

Проверено по `app/core/runner.py` (`_execute`, `_log_line`) — раннер запускает pytest
как обычный subprocess и построчно льёт его `stdout`/`stderr` (объединённые,
`STDOUT`→`STDOUT`) в `run_events` одной колонкой `line`, без привязки к nodeid и без
структуры:

- **Кадров UI-теста в реальном времени нет.** Для стендов с `use_env_flag` раннер сам
  выставляет `env["HEADLESS"] = "1"` перед запуском (`runner.py:341`) — браузер Playwright
  внутри тестов работает без головы, скриншотов по шагам никто не делает и никуда не
  шлёт. То, что показано в мокапе «Кинолента» и на вкладке «Кадры» в «Сплите» — это шаги
  allure (`allure_report.parse_results`, есть имя и статус каждого шага), а не картинка
  браузера; кадра для них физически нет.
- **Консоли по одному тесту прогона нет.** `run_events` — это общий лог всего процесса
  pytest целиком, одна строка = одна строка вывода, без маркировки, какому nodeid она
  принадлежит. Показать в окне теста «вывод pytest только для этого теста» сейчас нельзя
  — придётся либо гадать по паттернам вывода pytest (заголовки FAILED/PASSED, трейсбеки),
  либо получать разметку от источника.
- Видео/трейс Playwright после теста также нигде не сохраняется и не привязывается к
  run_id/nodeid — раннер не знает о существовании файлов, которые тестовый проект мог бы
  положить в свою рабочую директорию.

## План этапа 2

1. **Скриншоты шагов от источника, а не от раннера.** test_hub не встроен в процесс
   pytest и не может сделать кадр браузера сам — кадр нужно получать из проекта тестов.
   Предлагается pytest-плагин (conftest.py/фикстура в проекте тестов), который на каждом
   шаге UI-теста делает `page.screenshot()` и отправляет его в новый эндпоинт test_hub
   (`POST /api/runs/{run_id}/screenshot` с nodeid и номером шага) — тогда «Кинолента» и
   вкладка «Кадры» получат настоящий кадр браузера вместо шага allure без картинки.
   `HEADLESS=1` этому не мешает: скриншот в headless-браузере снимается так же, просто
   не выводится на экран.
2. **Playwright video/trace как fallback.** Если плагин на шаг не подключён или тест
   уже упал до первого шага, тестовый проект может включить `--video=retain-on-failure`
   и `--tracing=retain-on-failure` в своей playwright-конфигурации и после прогона
   положить файлы в `allure-results` рядом с отчётом теста (allure их уже умеет
   прикладывать как attachment) — раннер тогда получает готовые видео/трейс через тот же
   `allure_report.parse_results`, без отдельного API.
3. **Разбор вывода pytest по nodeid.** Чтобы окно теста показывало консоль только одного
   теста, а не весь `run_events`, вывод pytest нужно размечать при записи в `_log_line`:
   либо запускать pytest с `--tb=long -rA` и парсить его секции (`PASSED`/`FAILED`
   `test_module.py::test_name`, трейсбек до следующего заголовка), либо (надёжнее) идти
   тем же путём, что и со скриншотами — плагином, который явно логирует
   `[nodeid] <строка>` в stdout, и раннер при записи строки в `run_events` дополнительно
   пишет распознанный nodeid отдельной колонкой (миграция таблицы `run_events`). Второй
   путь не зависит от формата вывода pytest и не ломается при апгрейде pytest.
4. Порядок запуска в проекте тестов, «Запросы» (HTTP-строки с методом/кодом) в варианте
   «Сплит» уже получится из размеченной по nodeid консоли — отдельного API для них не
   нужно, только фильтрация строк по паттерну запроса на фронтенде.

Всё из плана — доработки в проекте тестов (плагин, конфигурация Playwright) и в
`app/core/runner.py`/схеме `run_events`; в этой миссии (этап 1) код не менялся.
