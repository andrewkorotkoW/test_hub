# Визуальный аудит test_hub — «как сейчас» + реальные данные

Миссия: `docs/missions/2026-09-29_visual_audit.md`. Это первый этап (только чтение,
код `app/`/`ui/` не менялся — проверено `git diff` в конце работы). Второй этап

## Важная поправка к тексту миссии: coverage_v3 существует

Миссия ссылается на `docs/missions/redesign/coverage_v3/` как на путь, которого
«нет в репозитории», и предлагает вместо неё брать `coverage-a-tree` из
`run_window/` как временную замену. **Это не так на момент выполнения этой
задачи**: `docs/missions/redesign/coverage_v3/` в репозитории есть (коммит
`ff6e951`, «карта покрытия v3, минимализм (F одна карта, G светофор)»), со
своими `mockups.html`, `collect_data.py`, `data.snapshot.json` и скриншотами
`coverage-f-onemap-{light,dark}.jpg` / `coverage-g-traffic-{light,dark}.jpg`.
Судя по всему, миссия была написана до того, как эта папка попала в общую
историю, либо в параллельной ветке. Проверено: `git log --oneline -- docs/missions/redesign/coverage_v3/`
показывает коммит `ff6e951` в истории текущего `HEAD`.

**Для следующих исполнителей:** используйте реальный `coverage_v3/` (варианты
F и G) как эталон минимализма для карты покрытия, а не `coverage-a-tree` —
он тоже неплохой референс (дерево разделов, светофор без легенды), но
`coverage_v3` явно ближе к правилу «один главный визуал, ≤5 чисел» этой
миссии, потому что именно под это правило и был сделан.

## Как собраны данные

`workspace/test_hub.db` в этом воркtree — копия боевой БД `test_hub`
(`PycharmProjects/test_hub/workspace/test_hub.db`, ~3.6 МБ, 39 прогонов по
3 проектам). Боевой файл не менялся, только читался и копировался. В копию
дополнительно добавлен проект **Demo** (`app.db._seed_demo_project`) — в
боевой БД его ещё не было, потому что сидируется он только на пустой БД
(`_seed_if_empty`), а боевая БД не пустая с более раннего момента, чем
появился Demo в коде.

Сервер поднят из копии на `127.0.0.1:8711` (`TH_TG_BOT_TOKEN=` пустой —
боевой телеграм-бот не трогается, `TH_DEMO_PORT=8712` — отдельно от боевого
демо-сервиса на 8710). Вход — `qa/qa`. После работы сервер остановлен
(см. `git status`/процессы), копия `workspace/test_hub.db` удалена — не
осталась мусором (она и так в `.gitignore`: `workspace/*.db`).

**Какой проект полнее по данным:** однозначно **VSHGU** — 2 стенда
(develop/stage), 20 прогонов за 21–28.09.2026, 34 известных дефекта (xfail),
275 тестов с историей ≥3 прогонов (из них 167 реально флапали хотя бы раз),
маршрутов в покрытии 595 (84 закрыто тестами). **Demo** в этой копии БД —
пустое состояние: проект только что засеян, реальных прогонов ещё не было
(это видно на скриншотах `project-dashboard-demo-*.jpg` и `xfail-demo-*.jpg`
как легитимный текстовый empty-state, а не баг). `Velo_bot` и `bike_fit` —
старые проекты владельца без стендов (стенды удалены), но с реальной историей
прогонов 14–25.09.2026 — использованы только для общего таймлайна активности
по дням в `data.snapshot.json` (см. ниже), детальных данных (флаки/xfail/
покрытие) по ним не собирали — вне списка страниц миссии.

## Чего нет в данных (честно, для report.md следующего этапа)

- **«Сколько xfail закрыто за месяц»** — не хранится нигде: `xfail_registry`
  не ведёт историю закрытых записей, закрытие — это просто `DELETE` строки.
  Посчитать без изменения схемы (миграция вне рамок этой задачи) нельзя.
- **«История выполнения расписания за неделю»** — в `schedules` хранится
  только `last_run_id` (последний прогон), не журнал. Честная замена в
  `data.snapshot.json.vshgu.schedule_history` — прогоны, запущенные
  сервисным логином `tg_bot` (это и есть прогоны по cron, см.
  `app/tg_bot.py`/`TH_TG_SERVICE_LOGIN`), у VSHGU таких 5 за 21–28.09.2026.
- **«История прогонов по дням минимум за 2-4 недели»** — у одного VSHGU
  реальной истории только ~7 дней (20 прогонов). Расширено объединением
  с Velo_bot/bike_fit (`runs_timeline_daily` в snapshot) — вместе получается
  9 дней с активностью в диапазоне 14–28.09.2026 (2 недели календарно, но не
  все дни внутри с прогонами — реалистичная редкая история QA, не ежедневная).

## Файлы

- `before/*.jpg` — 22 скриншота (11 страниц/вкладок × 2 темы), 1440px,
  через Playwright (`export_screenshots.py`), вход `qa/qa`, живой сервер на
  копии боевой БД.
- `collect_data.py` — тянет реальные данные через API живого test_hub
  (`/api/projects`, `/runs`, `/flaky`, `/xfail`, `/schedules`, `/coverage`,
  `/stats`) — те же числа, что видит qa на страницах, без пересчёта вручную.
  Запуск описан в docstring файла.
- `data.snapshot.json` — результат запуска `collect_data.py`: карточки всех
  4 проектов (кольцо/спарклайн за 10 прогонов), общий таймлайн прогонов по
  дням (`runs_timeline_daily`), и блок `vshgu` — 20 последних прогонов,
  полный флаки-реестр (275 тестов, `score`/`last_statuses` до 20 прогонов на
  тест), полный xfail-реестр (34 дефекта), расписания + производная история
  их выполнения, кэш покрытия (595 маршрутов) и агрегаты статистики по
  разделам стенда develop.
