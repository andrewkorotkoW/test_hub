# Визуальный аудит test_hub — итоговый отчёт

Миссия: `docs/missions/2026-09-29_visual_audit.md`. Опирается на
`README.md` (t1, «как сейчас» + реальные данные), `mockups.html` +
`*-proposal-{light,dark}.jpg` (t2, «как предлагаем») и `qa_notes.md` (t3,
сверка макета с миссией/`DESIGN.md`/данными). Все три документа прочитаны
целиком перед написанием; ничего сверх зафиксированного там не добавлено.

## Страница → что было → что предлагаем → данные → оценка

| Страница | Что было | Что предлагаем | Данные (есть/нет) | Оценка |
|---|---|---|---|---|
| **Проекты** | Список карточек-кружков с инициалами и числом стендов — только текст (`ui/projects.js`). | Карточка: кольцо % последнего прогона, спарклайн стабильности за 10 прогонов, светофор, строка «что важно» вместо списка. | **Есть.** `/api/projects` (мета) + `/api/projects/{name}/runs` (история для кольца и спарклайна) + `/api/projects/{name}/flaky` (число нестабильных для строки «что важно») — все три эндпоинта уже отдают нужные данные, `collect_data.py` считает кольцо/спарклайн на своей стороне из тех же ответов, нового backend не нужно. | Польза высокая (первый экран после логина), сложность низкая (только фронтовая агрегация существующих ответов API). |
| **Дашборд проекта** | Уже частично визуален (6 KPI-карточек, кольцо статусов, столбцы passed/failed, график длительности) — «Тесты по областям» пусто текстом, итого 6 KPI + кольцо + 2 графика на первом экране. | Кольцо-% (1) + 4 KPI = ровно 5 чисел на первом экране; лента прогонов и список xfail спрятаны в `<details>` ниже. | **Есть.** Все используемые числа — часть текущего API дашборда (`ui/project.js:1353-1360`), макет не вводит новых полей, только убирает 2 KPI и переносит ленту/xfail в раскрытие. | Польза высокая (самая посещаемая вкладка), сложность низкая (перекомпоновка существующих виджетов, без новых данных). |
| **История прогонов** | Чистая таблица (id/статус/стенд/цель/начат/длительность/кем), без визуала. | Таймлайн по дням — цветные столбики (высота — число тестов, цвет — светофор статуса), клик раскрывает прогон, фильтр по стенду. | **Есть.** `/api/projects/{name}/runs` уже отдаёт статус, стенд и `counts` на каждый прогон — агрегация по дням делается на фронте (ровно так, как это уже сделано в `collect_data.py:daily_timeline` для макета). Единственная оговорка не про данные, а про их объём: реальной истории VSHGU только ~7 дней (20 прогонов) — на боевой БД таймлайн первое время будет коротким. | Польза средняя, сложность низкая (группировка уже открытых данных, без новых полей). |
| **Флаки** | Таблица тестов (запуски/падения/% нестабильности) + 3 точки последних статусов. | Полоса «упал/прошёл» за 20 прогонов на каждый тест + спарклайн, сверху общее кольцо «индекс стабильности». | **Есть.** `/api/projects/{name}/flaky` уже отдаёт `last_statuses` длиной до 20 прогонов на тест (275 тестов в снимке) — ровно тот ряд, что нужен для полосы; кольцо считается на фронте как доля тестов без флипа. | Польза средняя-высокая (это страница специально «про нестабильность»), сложность средняя (компонент полосы на 20 сегментов + агрегирующий подсчёт для кольца, но без новых backend-полей). |
| **Известные дефекты (xfail)** | Длинная таблица (тест/причина/стенд/с какого числа/последний прогон/состояние), причины на 3-5 строк каждая. | Таймлайн «с какого прогона живёт дефект» (длина полосы — возраст, цвет — стенд), счётчик «сколько закрыли за месяц». | **Частично.** Возраст и стенд — есть в текущей записи xfail, таймлайн строится без новых данных. Счётчик «закрыто за месяц» — **нет**: `xfail_registry` не ведёт историю закрытий, закрытие — это `DELETE` строки без следа; в макете это честно показано как «—» с подписью «история закрытий не хранится в БД». Без миграции схемы (добавить лог закрытий) метрику получить нельзя. | Польза средняя, сложность средняя (таймлайн — низкая, но полноценный счётчик закрытий требует миграции БД, которая выходит за рамки макета). |

Замена в макете — прогоны сервисного логина `tg_bot` (это и есть прогоны по cron) как прокси-история; работает, пока на стенд приходится одно расписание, но не различает несколько расписаний на одном стенде — тогда понадобится либо `schedule_id` в `runs`, либо отдельный журнал выполнений расписания. | Польза средняя, сложность средняя-высокая (визуал сетки простой, но корректная история выполнения по расписанию требует доработки схемы при нескольких расписаниях на стенд). |
| **Тест-кейсы** | Страницы/вкладки в `ui/` нет вообще — есть только API (`app/core/test_cases.py`, миссия `2026-09-29_testcases_stage2.md`). | Кадры шагов «кинолентой» в карточке кейса (реюз принятого `docs/missions/testcases/mockups.html`, вариант «Дерево + карточка»). | **Частично.** Скриншоты к тест-кейсам уже реально синкаются из allure (`sync_run_attachments`, привязка к номеру шага) — это готовая фича этапа 2 «Тест-кейсы», не то же самое, что кадры UI-теста в реальном времени. Отдельно: «живая» кинолента во время прогона (окно прогона) — это другая, ещё не реализованная фича: раннер сейчас не умеет слать кадры браузера в реальном времени, для неё по плану `docs/missions/redesign/run_window/README.md` нужен новый эндпоинт `POST /api/runs/{run_id}/screenshot`, которого пока нет. | Польза высокая (наглядность кейсов — то, чего сейчас нет вообще), сложность высокая: самой вкладки «Тест-кейсы» ещё нет в `ui/`, это отдельная незакрытая миссия, а не доработка существующей страницы. |

## Порядок внедрения

Список отсортирован по соотношению польза/сложность (сначала — где отдача
выше, а работы меньше):

1. **Дашборд проекта** — самая посещаемая страница, все данные уже в API, нужна только перекомпоновка существующих виджетов (5 чисел вместо 6+, лента и xfail — в раскрытие).
2. **Проекты** — первый экран после входа, кольцо/спарклайн/светофор считаются на фронте из уже открытых `/runs` и `/flaky`, без нового backend.
3. **Статистика** — по заключению QA (`qa_notes.md`) это самый явный кандидат («стена чисел» без изменений), а данные для замены (per-section агрегаты, история passed) уже есть в `/stats`.
4. **Флаки** — история до 20 прогонов на тест уже хранится (`last_statuses`), нужен только компонент полосы и подсчёт кольца стабильности.
5. **История прогонов** — агрегация по дням из уже открытого `/runs`, простая, но менее приоритетная, чем дашборд/проекты, потому что реальной глубины истории пока мало (~7 дней на VSHGU).
6. **Сайдбар/шапка** — маленький, но постоянно видимый индикатор; данных для него не нужно собирать отдельно (тот же источник, что и для карточек Проектов), можно внедрить попутно с любым из пунктов выше.
7. **Известные дефекты (xfail)** — таймлайн возраста строится без новых данных, но метрика «закрыто за месяц» без миграции схемы недостижима — либо убрать её из первого экрана, либо сначала завести журнал закрытий.
8. **Расписания** — календарная сетка сама по себе простая, но честная история выполнения расписания нужна только как прокси (прогоны `tg_bot`), который ломается при нескольких расписаниях на одном стенде — до нормализации это не критично, но заранее нужно решить, устраивает ли владельца такое приближение.
9. **Тест-кейсы** — самая высокая потенциальная польза (сейчас такой страницы нет вообще), но и самая высокая стоимость: сама вкладка ещё не реализована в `ui/`, это отдельная незакрытая миссия этапа 2, а «кинолента» кадров зависит от неё же (скриншоты синкаются, но карточки кейсов с реальными кадрами ещё нужно собрать в интерфейсе).

И `README.md` (t1), и `qa_notes.md` (t3) фиксируют одно и то же: текст
миссии `docs/missions/2026-09-29_visual_audit.md` ссылается на
`docs/missions/redesign/coverage_v3/` как на путь, которого «нет в
репозитории», и предлагает вместо неё временную замену
`coverage-a-tree` — но на момент выполнения аудита `coverage_v3` в
репозитории уже есть (коммит `ff6e951`, варианты F/G, «карта покрытия v3,
минимализм»). Исполнители t1/t2 использовали реальный `coverage_v3` как
эталон стиля для остальных макетов, а не `coverage-a-tree` — это не влияет
на состав отчёта (страница «Покрытие» не входит в обязательный список из
9 разделов миссии, `coverage_v3` упоминалась только как справочный
эталон), но стоит поправить сам текст миссии или явно подтвердить выбор
`coverage_v3`, чтобы следующие исполнители не ориентировались на
несуществующий фолбэк.

## Открытые замечания QA

Ниже — то, что `qa_notes.md` (t3) отметил как расхождение с миссией/
`DESIGN.md`, но не исправлял (правка макета не входит в задачу QA и не
входит в задачу этого отчёта). Порядок — по убыванию значимости из
`qa_notes.md`:

1. **JPG 1400px вместо 1440px** — во всех 18 экспортированных файлах
   (`*-proposal-{light,dark}.jpg`, 9 разделов × 2 темы), при том что миссия
   прямо требует 1440px. Причина — в `export_proposal_screenshots.py`:
   скриншот снимается с элемента `.frame`, который лежит внутри
   `.wrap{max-width:1400px}`, а не с полного viewport 1440px.
2. **Точка «цвета проекта» из `DESIGN.md` (Layout) не реализована в шапке
   страницы** — в шапке дашборда стоит health-индикатор вместо неё, сам
   CSS-класс `.dot` (14px, с рамкой/тенью, описанный в токенах) нигде не
   подключён ни на одной из 9 страниц.
3. **KPI-типографика занижена инлайн-стилями в 3 из 9 разделов** —
   Дашборд (20px), Расписания и Статистика (17px) вместо токена
   `typography.kpi.fontSize=26px`; Xfail при этом использует корректные
   26px — непоследовательно.
4. **`h1` везде 20px вместо токена 22px** — систематическое отклонение,
   во всех 9 заголовках разделов одинаково, то есть осознанное, но не по
   `DESIGN.md`.
5. Малые/спорные пункты: текстовая легенда «develop»/«stage» на странице
   Xfail (единственное место с подписанной легендой рядом со светофором,
   что противоречит духу правила «светофор без легенды»);
   `.frame{border-radius:18px}` — не входит ни в один токен `rounded.*`
   (ближайший — `rounded.card=16px`); разделы «Флаки» и «Статистика» — на
   грани правила «≤5 чисел на экране», если считать в буквальном смысле
   каждое числовое начертание на странице целиком (а не только сводный
   блок) — сами списки под сводкой при этом являются прямым ответом на
   «где проблемы», как и требует миссия для этих двух разделов, поэтому
   QA не считает это нарушением по существу.
