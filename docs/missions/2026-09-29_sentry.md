# Миссия: подключение test_hub к Sentry — блок ошибок продукта для QA

Записано 29.09.2026 по просьбе владельца. Стартует после текущих миссий (окно прогона,
тест-кейсы, визуальный аудит).

## Зачем

QA во время и после прогона хочет видеть, что происходило в самом продукте (портал ВШГУ) на
стенде: какие ошибки прилетели в Sentry за время прогона, не связаны ли падения тестов с
ошибками бэкенда/фронта. Сейчас для этого нужно ходить в Sentry руками.

## Что должно получиться

1. **Настройка** через `.env`/`app/config.py`: `TH_SENTRY_URL` (базовый URL инстанса, например
   `https://sentry.example.ru`), `TH_SENTRY_TOKEN` (auth token, только чтение), `TH_SENTRY_ORG`.
   Привязка стенда к Sentry-проекту и environment — в настройках стенда (`stands`: новые
   колонки `sentry_project`, `sentry_environment` через `_migrate_add_column`; правит qa в
   форме стенда). Без настроек блок показывает «Sentry не подключён» и ничего не ломает.
2. **Клиент** `app/core/sentry.py`: чтение issues и events через Sentry Web API
   (`GET /api/0/projects/{org}/{project}/issues/?query=environment:<env> firstSeen:>…`,
   `GET /api/0/issues/{id}/events/latest/`), таймаут 5 с, кэш ответов 60 с, аккуратная обработка
   401/403/429/недоступности (в UI — понятная подпись, в лог — причина). Токен в ответы API
   test_hub и в лог не попадает.
3. **API test_hub** (роль qa, остальным 403):
   - `GET /api/projects/{name}/stands/{stand}/sentry/issues?since=&until=` — список issues
     (title, culprit, level, count, userCount, firstSeen, lastSeen, permalink);
   - `GET /api/runs/{id}/sentry` — issues за окно прогона (started..finished, +5 мин после)
     на стенде прогона, с пометкой «новые в этом окне» (firstSeen внутри окна).
4. **UI — отдельный блок для QA**:
   - на странице проекта, вкладка «Дашборд»: карточка «Ошибки продукта (Sentry)» — за
     последние 24 ч по стенду: одно число новых issues, светофор, 5 последних строк
     (уровень, заголовок, сколько раз, ссылка в Sentry). Видна только роли qa;
   - в карточке прогона (вкладка «Запуск», окно «Сплит» из миссии `run_window_stage2`) —
     вкладка «Sentry»: issues за окно прогона, новые выделены; клик по строке — ссылка в Sentry;
   - стиль по `DESIGN.md` (светофор, ≤ 5 чисел), обе темы.
5. **Тесты**: конфиг без настроек → блок отключён; клиент на мок-сервере (успех, 401, 429,
   таймаут, кэш); права ролей; окно прогона; UI-логика без браузера. Существующие тесты проходят.

## Ограничения

- Только чтение из Sentry, ничего не создавать и не менять там. Секреты только в `.env`
  (в `.env.example` — пустые значения и комментарий).
- Стенды VSHGU не трогать, прогоны не запускать. Коммиты небольшие, на русском.
- README: раздел «Sentry» — как получить токен и заполнить настройки стенда.

## Приёмка

С настроенным `.env` и стендом develop: на дашборде проекта у qa виден блок с ошибками за
сутки, у manager блока нет; у завершённого прогона на вкладке «Sentry» — issues за его окно,
ссылки открываются в Sentry. Без `.env` — подпись «Sentry не подключён», ошибок в логе нет.
