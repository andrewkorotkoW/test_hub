# Отчёт: профиль пользователя, регистрация с одобрением, аватар в шапке

По миссии `docs/missions/2026-10-10_user_profiles.md`, после слияния веток
t1 (`eb2ceac`/`6f78804` — бэкенд), t2 (`b592bd3`/`49c32c7` — UI), t3
(`2f4881e` — тесты), и отдельной доработки доступа к проектам по ролям
(`965941b`/`7ad07b3` — `user_projects` для manager/customer), все пять веток
уже слиты в `main` (merge-коммиты `eb2ceac`, `b592bd3`, `7ad07b3`, `e9100ab`).
Этот отчёт и обновление README — финальный шаг, код/тесты не менялись.

## Часть 1 — схема и бэкенд

Сделано полностью по контракту миссии (`app/db.py`, `app/routers/auth.py`,
`app/routers/users.py`, `app/schemas.py`):

- миграция `users`: `full_name`, `position`, `project REFERENCES projects(name)`,
  `avatar_filename`, `status TEXT NOT NULL DEFAULT 'active' CHECK (...)` —
  добавлены через `_migrate_add_column`, существующие строки получают
  `status='active'` автоматически (SQLite `ALTER TABLE ADD COLUMN` с `DEFAULT`
  не требует пересоздания таблицы);
- `POST /api/auth/register` — публичный, `status='pending'`, `role='customer'`,
  без сессионной куки;
- `POST /api/login` при `status != 'active'` — `403` с текстом «Заявка ещё не
  одобрена» / «Заявка отклонена» вместо `401`;
- `PUT /api/users/{login}/approve|reject` (`require_roles("qa")`, `superadmin`
  проходит любой `require_roles`) — одобрение с опциональным выбором роли,
  отклонение как soft delete (`status='rejected'`, без удаления строки);
- `GET /api/me` / `GET /api/users` — расширенный payload
  (`full_name`/`position`/`project`/`status`/`avatar_url`);
- `PUT /api/me` — самостоятельное редактирование ФИО/должности/проекта, роль и
  статус недоступны;
- `POST/GET /api/me/avatar`, `GET /api/users/{login}/avatar` — загрузка/отдача
  PNG/JPG, тот же лимит размера (`TH_TESTCASE_ATTACHMENT_MAX_BYTES`) и проверка
  типа, что у вложений тест-кейсов.

**Отклонение от буквы плана** (сознательное, зафиксировано в ходе задачи):
пункт 6 плана требовал расширить payload «`GET /api/me` / `GET /api/users`», но
не затрагивал `POST /api/login`, `POST/PUT /api/users/{login}` (create/update) —
их ответы покрыты старыми тестами со строгим сравнением словаря
(`tests/test_auth.py`, `tests/test_qa_crud.py`), которые миссия запрещала
трогать. Решение — отдельные «старые» payload-функции для этих трёх
эндпоинтов (`_login_payload`, `_user_payload_min`), расширенные `_me_payload`/
`_user_payload` — везде остальном. Побочных эффектов на функциональность нет.

## Часть 2 — страница профиля и регистрация

`ui/profile.html`+`profile.js`, `ui/register.html`+`register.js` — по плану:
своя ФИО/должность/проект (редактируемые, `PUT /api/me`), загрузка аватара;
публичная форма регистрации (логин/пароль/ФИО/должность/проект — select из
`GET /api/projects/names`, отдельного облегчённого публичного эндпоинта,
созданного именно для этой формы); экран «Заявка отправлена, ждите одобрения»
без автовхода. На странице входа (`ui/index.html`) — ссылка «Нет аккаунта?
Зарегистрироваться»; при `403` от сервера текст ошибки показывается как есть
(`ui/login.js`), не универсальное «неверный логин/пароль».

## Часть 3 — аватар в шапке и одобрение заявок

`ui/common.js::renderHeader` — кружок-аватар (картинка либо инициалы по
фолбэку, тот же приём, что у логотипов проектов) рядом с логином и текстовым
бейджем роли (бейдж не заменён, оставлен по решению миссии «на усмотрение
исполнителя»), клик ведёт на `profile.html`. Битый файл аватара на диске при
выставленном `avatar_url` — откат на инициалы через `onerror` у `<img>`.

`ui/admin.html` раздел «Пользователи» — колонки ФИО/Должность/Проект/Статус;
отдельный блок «Заявки на регистрацию» (`status='pending'`) с кнопками
«Одобрить» (с выбором роли)/«Отклонить».

**Дополнение сверх плана** (сделано отдельной задачей после слияния
частей 1–3, коммиты `965941b`/`7ad07b3`): поле `project` в профиле и в форме
регистрации само по себе не ограничивало видимость проектов — миссия это не
уточняла явно, но было логическим следствием «проекта, в котором пользователь
задействован». Добавлена таблица-связка `user_projects` для `manager`
(несколько проектов, переносится из `users.project` при одобрении) и фильтр
`GET /api/projects` по роли: `qa`/`superadmin` — всё, `manager` — через
`user_projects`, `customer` с заполненным `project` — один проект,
`project IS NULL` (включая сервисную учётку Telegram-бота) — общий fallback
«видно всё» без проверки по конкретному логину (первая версия с явной
проверкой `login == TH_TG_SERVICE_LOGIN` была отклонена ревью как
нежелательный частный случай). `POST /api/projects` теперь разрешён и
`manager`.

## Часть 4 — тесты и прогон

- `tests/test_user_profiles.py` (35 тестов) — регистрация → pending → логин
  отклонён → одобрение (с ролью и без) → логин успешен → отклонение заявки;
  `PUT /api/me` (включая игнор посторонних полей `role`/`login`/`status`);
  загрузка/отдача аватара (успех, замена, отказ не-PNG/JPG, отказ по размеру,
  чужой логин для `GET /users/{login}/avatar`); миграция `users` на старой
  схеме таблицы (3 колонки) — новые поля проставляются с дефолтами, в т. ч.
  `status='active'` существующим строкам.
- `tests/test_project_access.py` (9 тестов) — видимость проектов по ролям,
  перенос `users.project` → `user_projects` при одобрении `manager`, не-перенос
  для `customer`, 403 на создание проекта для `customer`, регрессия на
  видимость сервисной учётки бота как частный случай общего `NULL`-fallback.
- Правка `tests/test_roles_crud.py` — `POST /api/projects` вынесен из списка
  «manager запрещён», так как теперь разрешён.

**Полный прогон (взят из этой сессии, см. ниже «Живая проверка» про README,

БД `workspace/test_hub.db`, `TH_TG_BOT_TOKEN=""`, `TH_DEMO=0`, боевой сервер на

### Найденный дефект (не исправлен — код/тесты по условиям задачи не трогать)

При живой проверке страницы профиля обнаружено: после загрузки аватара
заглушка-кружок с инициалами (`#profile-avatar-placeholder`) не скрывается
визуально, хотя `ui/profile.js::renderAvatar` корректно выставляет ей атрибут
`hidden` (подтверждено через `getComputedStyle` в Playwright: `hiddenAttr:
true`, `display: flex`). Причина — `.profile-avatar-placeholder-lg` в
`ui/style.css` задаёт `display: flex` без парного правила
`.profile-avatar-placeholder-lg[hidden] { display: none; }`, которое для
аналогичных переключаемых блоков в этом же файле уже есть (`.modal-overlay[hidden]`,
`.run-split[hidden]` и другие). На сохранение данных не влияет — только
отображение; задокументировано в README (раздел «Профиль и регистрация»,
«Известный дефект») и видно на скриншоте `profile_page_light.png` (круг «ИМ»
под карточкой «Аватар»). Этот дефект не зафиксирован ни в одном из коммитов
миссии — ни бэкенд/UI-веткой, ни веткой тестов (тесты проверяют DOM-атрибут
`hidden`, не computed style, поэтому не ловят такие CSS-коллизии).
